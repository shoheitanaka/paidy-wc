## 指摘
### [R1-1][Medium][tests/Unit/test-paidy-webhook-permission.php, tests/Unit/test-paidy-payment-id-format.php]
今回の主修正（`GET /payments/{id}` を POST で呼んでいた不具合の GET 化、200 以外・通信エラーで `null`）を固定するテストが無い。
HTTP モックが `method` を見ず常に 200 を返すため、`wp_remote_post()` に戻しても 200 チェックを消しても全件通る。
あわせて、未認証リクエストのテストが 403 だけを見ていて `paidy_verification_failed`（同じ 403）と区別できない点、
「冪等性」テストが実際には processing 分岐を通っている点（ガード自体は別テストで固定済み）も直す。
**修正方針:** モックで HTTP メソッドを記録し GET を assert、404 / 500 / 通信エラーで `null` と注文 pending のままを確認するテストを追加。REST テストでエラーコード `paidy_unauthorized` を assert、冪等性テストの名前を実態に合わせる。

### [R1-2][Low（サブエージェント判定 Medium から引き下げ）][includes/gateways/paidy/class-wc-paidy-endpoint.php:181-185]
`paidy_trust_proxy_headers` を有効にすると `X-Forwarded-For` の先頭を採用するため、XFF に追記するプロキシの背後では偽装できる。
引き下げの理由: 運用者の明示的なオプトイン時だけで、裏取り（ID・order_ref・金額・状態）があるため注文を支払い済みにはできない。
右端を採ると多段プロキシ（CDN + LB）で正規の通知を拒否し、JP4WC 2.9.6 と同種の「通知拒否 → 自動キャンセル」障害になり得るので、JP4WC と独立に変えない。
**修正方針:** backlog B-14（JP4WC で信頼するプロキシ段数などの方針を決めてから同期）。

## 確認して問題なかった点（サブエージェント + 自己確認）
- 署名の対象（raw body）とコールバックが解析する本文が同一、不正署名から IP 照合へフォールバックしない、鍵が空なら 500
- 鍵の選択 `'live' !== environment` は `set_api_secret_key()` と一致（`environment` 未設定 `''` も同じ扱い）
- 未認証で到達できる範囲に fatal なし。金額・order_ref の照合値は `paidy_make_order()` が送る値と一致
- `init` 11 遅延でも `rest_api_init` より前に登録される。旧コードの重複 `require_once`（JP4WC 併用時に再宣言 fatal の恐れ）が消えた
- 返金処理の既存の呼び出し元: 旧実装も（POST で 404 のため）判定は常に偽で、挙動は変わらない
- JP4WC 2.9.16 との差分は `docs/sync-with-jp4wc.md` の意図的な差分 7・8 のみ
