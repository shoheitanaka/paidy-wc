## 指摘
### [G1-1][Copilot][Low][includes/gateways/paidy/class-wc-paidy-apply-receiver.php:624]
`check_permissions()` が `get_param( 'application_id' )` を使うので、未署名のクエリ値が優先されて旧申込の不一致検査を通過できる。配列値では `preg_match()` が `TypeError`（664・1010 行の `state` も同様）
判定: 保留。クエリの優先は誤り — WordPress core の `get_param()` は `get_parameter_order()` の JSON → POST → GET の順で最初の値を返す（テスト環境の core で確認）。
body に `application_id` があればクエリは使われず、無いときは `process_receive_data()` が body のみを読んで `missing_application_id`（400）で終わる。
`state` は `verify_state_token()` / `consume_state_token()` が `is_string()` で弾く。配列の `application_id` で `TypeError`（500、状態は変わらない）は事実だが Low で、JP4WC から verbatim のコード
**対応:** backlog B-31（JP4WC へ PR）、baseline に `get_param()` の優先順を記載 / スレッド: https://github.com/SoftStepsEC/paidy-wc/pull/41#discussion_r4232057442

### [G1-2][Copilot][Low][includes/gateways/paidy/class-wc-paidy-apply-receiver.php:798]
設定更新とアクション発火の後に `paidy_received_data` の保存が失敗すると 500 を返し、event claim を解放するので、再送で副作用とアクションが重複する
判定: 保留。起きるのは直前の `update_option()` が成功した直後に DB 書き込みが失敗した場合だけ（同じ値の再保存は成功扱い）。重複するのは同じ鍵の再書き込み（冪等）と
アクションの再発火。失敗時に claim を解放して再送を許すのは JP4WC 2.9.16 の設計で、順序の入れ替えや claim の保持は JP4WC で設計してから同期する
**対応:** backlog B-32（JP4WC へ PR）/ スレッド: https://github.com/SoftStepsEC/paidy-wc/pull/41#discussion_r4232057519
